## 2026-08-02 — Two docs/02 assumptions don't hold against the real interim data
Inspected the actual `data/interim/` schemas before writing classification code (per the "verify before building" rule).

1. **Development applications data has no applicant/developer name field.** `docs/02` assumed "development application applicant fields name firms directly." The full 23-column schema of `development_applications.csv` (`application_type`, `application_number`, street/postal fields, `date_submitted`, `status`, `description`, `reference_file_number`, `folder_rsn`, ward fields, community meeting fields, `application_url`, `contact_name`/`contact_phone`/`contact_email`, `parent_folder_number`) has no owner/applicant field — `contact_name` is a City of Toronto planner (e.g. "Marr, Tyler", `@toronto.ca` email), not the developer. The applicant name likely exists only on the per-application detail page behind `application_url` (`app.toronto.ca/AIC/...`), which is not currently scraped and wasn't in scope for Phase 0/1.
2. **Contribution records have no occupation field.** `contributions.csv`'s 16 columns (`contributor`, `postal_code`, `amount`, `amount_returned`, `contribution_type`, `description`, `contributor_type`, `date_received`, `candidate`, `office`, `ward`, `registrant_type`, `source_file`, `election`, `election_year`, `has_encoding_issue`) confirm what `docs/02` anticipated as a possibility ("where absent, do not guess") — occupation is absent.

**Consequence:** Signal 4 (occupation) drops out of the scoring entirely — not degraded, unavailable. Signal 3 (name matching) will be built from the lobbyist registry alone (firm names, client/parent company names, and registrant individuals with position titles, filtered to subject matters mentioning development/planning/zoning/land use — 7,878 of 14,504 lobbyist filings) rather than also cross-referencing development-application applicant names. This narrows Signal 3's reference universe but does not eliminate it. Scraping the AIC per-application pages to recover applicant names is a possible future enrichment, not attempted now — logged as a v2 candidate, not a blocker, per the same "note it and continue" logic used for the `Absent(Interest Declared)` finding.

## 2026-08-02 — Two scoring bugs caught by testing before donors.csv was trusted
Built `pipeline/transform/classify_donors.py` (Signals 1–3 per `docs/02`, scoped to Councillor + Mayor contributions, 23,041 rows). The first run scored 96.4% of all contributions above zero — an obviously wrong result for something meant to flag an unusual pattern, not describe the median donation. Investigated rather than shipping it.

1. **Temporal clustering alone was firing on 78% of all contributions.** Any candidate with a healthy donor base has 3+ people giving within *some* 7-day window purely from ordinary fundraiser timing (a gala, a push near nomination day or voting day). `docs/02` itself names this the "fundraiser-event pattern" and explicitly contrasts it with the "coordinated-firm pattern" (which requires a *shared address in the same window*) — I had scored the benign case at the same weight as the suspicious one. **Fix:** Signal 2 alone now contributes ~0 to the score; it only carries weight when it co-occurs with Signal 1 on the same postal code (`coordinated_firm_bonus`), matching docs/02's own framing.
2. **Signal 1's donor-count/aggregate-amount threshold ignored donation size entirely**, even though docs/02's stated signature is specifically "donations *at or very near the contribution limit*." The top flagged cluster pre-fix was 10 donors averaging $192 (16% of the councillor limit) at one postal code — ordinary neighbours, nothing like the signature. Checked the full distribution of `near_limit_share` (fraction of a cluster's donations ≥90% of the office's limit) across all 1,066 clusters that cleared the count/amount threshold: strongly bimodal (415 clusters under 10% near-limit, 391 over 70%, a real valley in between), confirming two genuinely different populations were being flagged identically. **Fix:** added `ADDRESS_NEAR_LIMIT_MIN_SHARE = 0.3` as an additional gate, and the address-cluster score is now scaled continuously by `near_limit_share` rather than flat.

**Result after both fixes:** 8.5% of contributions score above zero (was 96.4%), 4.2% score ≥0.5, 0.16% (36 rows) score ≥0.85. The top-scoring cluster after the fix (Perruzza, Anthony / Nathan Bierbrier, President, matched lobbyist registrant, 19 donors, 100% at the $1,200 limit, same postal code, 7-day window) is a legible, defensible example of the actual pattern docs/02 describes — the false-positive cluster (Takang, Gabriel, 10 donors averaging $192) no longer appears in the flagged set at all.

**Consequence:** this is exactly the kind of self-check the project's "would a hostile reader find a hole" bar demands, and it nearly shipped wrong. `docs/02`'s sensitivity-analysis section (strict/base/permissive thresholds) is still a Phase 3 task, not done here — but every threshold used (`ADDRESS_CLUSTER_MIN_DONORS`, `ADDRESS_CLUSTER_MIN_AMOUNT`, `ADDRESS_NEAR_LIMIT_MIN_SHARE`, `TEMPORAL_WINDOW_DAYS`, `TEMPORAL_CLUSTER_MIN_DONORS`, `NEAR_LIMIT_FRACTION`, and the `WEIGHTS` dict) is a named constant at the top of `classify_donors.py` specifically so that pass can vary them without touching the logic. Manual adjudication (top 300 donors by dollar value, disagreeing-signal records, random sample of 100 low-score records for a false-negative rate) per docs/02 is not done yet — logged as the next task, not skipped.

## 2026-08-02 — docs/03's Tier 1 vote↔development-application join does not exist; found a better Tier 2 signal instead
Before writing vote coding, checked whether `docs/03`'s Tier 1 ("If the development applications dataset carries an agenda item reference, use it... Confirm during Phase 0 whether this link exists") actually holds — this was never explicitly checked in Phase 0 (`phase0-findings.md` confirmed ward/date coverage for `development_applications.csv` but not an agenda-item join key). It does not hold: `development_applications.csv`'s `application_number` (format `"13 267299 NNY 08 SA"`, a City Planning file number) and `reference_file_number` (only 849/26,368 non-null, and not in agenda-item format either) share no format or values with `votes.csv`'s `agenda_item_number` (format `"2023.FM1.8"`, Year.Committee.ItemNumber). **Tier 1 direct join is not available — confirmed, not assumed. Falls back to Tier 2 + Tier 3 per docs/03's own contingency plan.**

While checking Tier 2 ("Committee provenance... usually recoverable from the vote record's meeting metadata"), found that the `committee` field in `votes.csv` is much weaker than expected: 42,857 of 45,665 votes (93.8%) are recorded as committee=`"City Council"`, because most items get their final recorded vote at Council even when they originated at a standing committee — the `committee` field shows *where the vote was cast*, not *where the item originated*. Only 434 rows show `committee="Planning and Housing Committee"` directly, for example.

**Better signal found:** the middle segment of `agenda_item_number` (e.g. `FM` in `2023.FM1.8`) is the City Clerk's own body-abbreviation code for where the item *originated*, and survives even when the recorded vote is at Council. There are 33 distinct codes. Verified a sample of the higher-volume/ambiguous ones live against `secure.toronto.ca/council/agenda-item.do` (via the browser tool — `WebFetch` gets the same Akamai 403 as the EFD site, same host, browser tool works):

| Code | Verified as | Development-relevant? |
|---|---|---|
| PH | Planning and Housing Committee | **Yes — blanket Tier 2** |
| PB | Toronto Preservation Board (sample item verified was a heritage designation under the Ontario Heritage Act) | **Yes — blanket Tier 2** (docs/03's "heritage designations where they gate development") |
| NY, TE, SC, EY | The 4 Community Councils | **Partial** — per docs/03's own phrasing ("Community Council *planning* items"), these need Tier 3 text filtering within them, not a blanket flag; community councils handle plenty of non-planning local business too |
| MPB | Mayor's Proposed Budget | No — matches docs/03's explicit capital-budget exclusion |
| RM | Review of the Order Paper | No — procedural |
| DM | Deferred/Ombudsman-referred items (sample verified: a Housing Commissioner role review) | No |
| FM | Formal/procedural Council matters (sample verified: election of Speaker) | No |
| CA | Civic Appointments Committee | No |
| IA | Administrative Inquiry (a member-inquiry mechanism, not a committee) | No |
| BL | Bills (introduction/passage of by-laws already decided elsewhere — procedural enactment, even though the boilerplate text mentions "Zoning By-laws") | No — procedural, not a decision on a specific application |
| EX, IE, EC, GG, HL, BU, AU, TTC, FWC | Executive, Infrastructure & Environment, Economic & Community Development, General Government, Board of Health, Budget, Audit, TTC, FIFA World Cup Subcommittee | No (name matches the already-known non-development committee list from the `committee` field) |
| PA, CT, ST, NC, TA, CR, DI, ZB, EP, TM | Not individually verified — combined ~120 of 45,665 rows (0.26%), immaterial | Falls through to Tier 3 text classification by default (safe default: real development content in the title/description still gets caught there) |

**Consequence:** `pipeline/transform/code_votes.py` codes `is_development` as: blanket true (high confidence) for PH/PB; Tier 3 keyword classification for everything else, including NY/TE/SC/EY. No code corresponds to "Committee of Adjustment appeals" (the third category docs/03 names) — Committee of Adjustment is a delegated quasi-judicial body whose decisions aren't voted on by Council directly, so this docs/03 category doesn't have a matching population in the vote record at all; noting this so the methodology page doesn't claim coverage of something the data can't provide.
