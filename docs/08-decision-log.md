## 2026-08-02 — Two scoring bugs caught by testing before donors.csv was trusted
Built `pipeline/transform/classify_donors.py` (Signals 1–3 per `docs/02`, scoped to Councillor + Mayor contributions, 23,041 rows). The first run scored 96.4% of all contributions above zero — an obviously wrong result for something meant to flag an unusual pattern, not describe the median donation. Investigated rather than shipping it.

1. **Temporal clustering alone was firing on 78% of all contributions.** Any candidate with a healthy donor base has 3+ people giving within *some* 7-day window purely from ordinary fundraiser timing (a gala, a push near nomination day or voting day). `docs/02` itself names this the "fundraiser-event pattern" and explicitly contrasts it with the "coordinated-firm pattern" (which requires a *shared address in the same window*) — I had scored the benign case at the same weight as the suspicious one. **Fix:** Signal 2 alone now contributes ~0 to the score; it only carries weight when it co-occurs with Signal 1 on the same postal code (`coordinated_firm_bonus`), matching docs/02's own framing.
2. **Signal 1's donor-count/aggregate-amount threshold ignored donation size entirely**, even though docs/02's stated signature is specifically "donations *at or very near the contribution limit*." The top flagged cluster pre-fix was 10 donors averaging $192 (16% of the councillor limit) at one postal code — ordinary neighbours, nothing like the signature. Checked the full distribution of `near_limit_share` (fraction of a cluster's donations ≥90% of the office's limit) across all 1,066 clusters that cleared the count/amount threshold: strongly bimodal (415 clusters under 10% near-limit, 391 over 70%, a real valley in between), confirming two genuinely different populations were being flagged identically. **Fix:** added `ADDRESS_NEAR_LIMIT_MIN_SHARE = 0.3` as an additional gate, and the address-cluster score is now scaled continuously by `near_limit_share` rather than flat.

**Result after both fixes:** 8.5% of contributions score above zero (was 96.4%), 4.2% score ≥0.5, 0.16% (36 rows) score ≥0.85. The top-scoring cluster after the fix (Perruzza, Anthony / Nathan Bierbrier, President, matched lobbyist registrant, 19 donors, 100% at the $1,200 limit, same postal code, 7-day window) is a legible, defensible example of the actual pattern docs/02 describes — the false-positive cluster (Takang, Gabriel, 10 donors averaging $192) no longer appears in the flagged set at all.

**Consequence:** this is exactly the kind of self-check the project's "would a hostile reader find a hole" bar demands, and it nearly shipped wrong. `docs/02`'s sensitivity-analysis section (strict/base/permissive thresholds) is still a Phase 3 task, not done here — but every threshold used (`ADDRESS_CLUSTER_MIN_DONORS`, `ADDRESS_CLUSTER_MIN_AMOUNT`, `ADDRESS_NEAR_LIMIT_MIN_SHARE`, `TEMPORAL_WINDOW_DAYS`, `TEMPORAL_CLUSTER_MIN_DONORS`, `NEAR_LIMIT_FRACTION`, and the `WEIGHTS` dict) is a named constant at the top of `classify_donors.py` specifically so that pass can vary them without touching the logic. Manual adjudication (top 300 donors by dollar value, disagreeing-signal records, random sample of 100 low-score records for a false-negative rate) per docs/02 is not done yet — logged as the next task, not skipped.

## 2026-08-02 — Variable 2 (motion direction / pro_dev_vote) built — a real, large coverage gap, reported honestly
Built `pipeline/transform/code_motion_direction.py`. `agenda_item_title` turned out to be the only reliable text field for motion direction — `vote_description` in `votes.csv` is almost always a terse procedural label ("Majority required - EX27.2 - Saxe - motion 2"), not the motion's actual content. The full text lives on each item's page (confirmed reachable via the browser tool, same site as the committee-code verification above), but reading it for every motion on all 246 development items (404 distinct motions) was out of scope for this pass — logged as a follow-up enrichment, not silently dropped.

**Results, and the honest limitation:**
- Of 246 development items, only the 235 "Adopt Item"/"Adopt Item as Amended" motions represent a final decision; **only 85 of those 235 (36.2%) have explicit approve/refuse/oppose language in the title** — the other 64% are classified `motion_direction="ambiguous"` and excluded, with the machine-readable reason `"no explicit approve/refuse/oppose language in item title"`. This mirrors docs/03's own treatment of deferrals ("Excluding them is cleaner than guessing. Report how many were excluded.") applied to the same underlying problem: the data doesn't reveal direction, and guessing on the single most scrutinized variable in the project would be worse than a smaller honest sample.
- **"Amend Item" motions (the docs/03 worked example — "reduce height/density/units → restrictive") are always excluded** — an amendment's direction (tightening vs loosening an application) is fundamentally not recoverable from the title alone, and this is the single largest gap versus docs/03's stated method. It would require reading each amendment's actual text.
- Net effect: of 45,665 total vote rows, only **1,176 (2.6%) are `included=True`** in the main specification — funneled down through is_development (22.7%) → Adopt-type motions only → title-resolved direction only (36.2%) → non-absent votes only. Of those 1,176, 1,144 are on `supportive`-direction items and only 32 on `restrictive` — a large class imbalance consistent with how Toronto planning practice actually works (most applications that reach a final vote are staff-negotiated approvals; outright refusals are the exception), but worth flagging as its own descriptive fact, not just a modeling nuisance.
- Member↔ward/office attribution via `member_terms.csv`, joined by name and vote date: **zero unmatched member/date combinations** across all 45,665 rows — the date-ranged join (rather than a flat lookup) worked cleanly, including correctly routing Robinson→Chernos Lin, Crawford→Kandavel, and McKelvie→Shan votes to the right ward/office/date range.
- Sanity-checked the `pro_dev_vote = (vote=="Yes") XOR (direction=="restrictive")` logic against every included row: correct in all cases (Yes+supportive → True, No+restrictive → True, etc).

Output: `data/interim/motions.csv` (404 development-item motions with direction + basis), `data/interim/votes_coded.csv` (all 45,665 member-votes, `included`/`exclusion_reason` on every row per docs/05).

**Consequence:** the 2.6% inclusion rate and the Amend-Item gap are exactly the kind of thing docs/03 predicted would be "the place where a critic will push," and now there's a real, measured number for it rather than a vague caveat — this belongs prominently in docs/04's Limitations section, not buried. A well-scoped follow-up (scraping full motion text for the 404 development-item motions, a bounded ~250-page task, not the open-ended kind Phase 0 ruled out) could recover a meaningfully larger sample; not attempted this session given time, flagged as the highest-value next enrichment for Phase 2/3.

## 2026-08-03 — Donor manual adjudication (docs/02): two more real fixes, worksheet built

Building the top-300 list surfaced two more real issues before any individual-level review was even useful:

2. **Returned contributions were counted at face value.** Spot-checking a top-300 entry (two donors each showing $10,000+ to mayoral candidate Anthony Furey) found `amount_returned` exactly equal to `amount` on the $10,000 rows — the campaign had rejected the over-limit portion and returned it in full, but the classifier was still crediting the donor with the full gross amount. ## 2026-08-03 · Phase 3 primary result: cannot distinguish the hypotheses

Built `pipeline/analyze/specification.py`, `sensitivity.py`, and `diagnostics.py` and ran them against the locked pre-registration. Installed `statsmodels`/`scipy` (not part of the original Phase 0 dependency list) to run the logistic regression and Spearman correlation.

**Population:** all 26 currently sitting members have a defined `dev_affiliation_share` and at least one included vote — full coverage, no missing members. 15 of 26 have a share of exactly 0.00 (no development-affiliated donors detected at all, at the base threshold); the rest range from 3.7% (Michael Thompson) to 32.4% (Anthony Perruzza). `data/processed/candidate_donor_mix.csv` published.

**Primary test (base threshold 0.5):** `dev_affiliation_share` coefficient = **−2.331** (p=0.283), 95% CI **[−6.588, 1.926]**, n=1,154 included votes across 26 members, clustered SE by member. **Wrong-signed relative to H1** (H1 predicts positive) and not statistically significant.

**Sensitivity analysis (strict 0.75 / base 0.5 / permissive 0.35):** direction is negative at all three thresholds — no flip. None reach significance (p=0.32, 0.28, 0.52). Member-level Spearman is also negative and non-significant at all three (rho=−0.23 to −0.29, p=0.15–0.30). `data/processed/candidate_donor_mix_all_thresholds.csv` published.

**Leave-one-out diagnostics (required in every case per the locked decision rule):** reran the base-threshold model 26 times, each time dropping one member. Coefficient stayed negative in all 26 reruns (range −4.70 to −1.68, zero sign flips); Spearman rho stayed negative in all 26 reruns too (range −0.38 to −0.21, zero sign flips). **The negative direction is not driven by any single influential member** — it's stable under leave-one-out. `data/processed/leave_one_out.csv` published.

**Applying the locked decision rule:**
- Not "supported" — never positive at any threshold.
- Not "refuted" outright, even though the coefficient is negative at all three thresholds, because the rule's own override fires first: **the base-threshold 95% CI [−6.588, 1.926] spans both an economically meaningful negative effect and an economically meaningful positive effect** (on the log-odds scale, −6.588 corresponds to an odds ratio near 0.001 — essentially never voting pro-development at full affiliation share — while +1.926 corresponds to an odds ratio near 6.9, a strong positive effect). The pre-registered rule states this exact condition triggers "cannot distinguish," and it does here.
- **Verdict: the data cannot distinguish H1 from its alternatives.** The direction leans consistently negative and that lean is robust to dropping any single member, but the confidence interval is too wide, at this sample size, to rule out a real positive effect in either direction. This is a direct consequence of the 2.6% vote-inclusion rate (1,176 of 45,665 votes) established in Variable 2's build — the sample is honestly small, and the analysis says so rather than rounding to a more dramatic headline.

**Consequence:** per docs/04 ("Write the null-result version of the hero copy before running the analysis... reporting your own weaknesses is what separates this from advocacy"), this is a legitimate, publishable outcome, not a failed analysis — but "cannot distinguish" is a more precise and more honest headline than either "no relationship" or "a relationship." The clearest path to a sharper answer is the still-open motion-text scrape (docs/08, 2026-08-02): growing the 2.6% vote-inclusion rate would narrow these confidence intervals, and the whole Phase 3 pipeline is built to be rerun against a larger `votes_coded.csv` without any changes to the specification itself.

Adopt-type and everything else unchanged from the original pass.

**Two false positives caught and fixed before trusting any output** (both found by actually reading the matched text, same discipline as the donor-classification manual adjudication):
1. 2. **Result after both fixes: only 4 of 141 Amend-type motions resolve** (2.8%) -- all four hand-verified clean: two heritage/planning-application refusals ("refuse the application," restrictive), one explicit height-increase amendment ("increasing height permissions to 12 storeys," supportive), one more application refusal. **Vote-level inclusion rate grows from 2.6% (1,176/45,665) to 2.8% (1,262/45,665)** -- real, but far more modest than hoped. **Honest finding, not a shortfall to paper over:** the large majority of Amend-type motions are about conditions, community benefits, process, and consultation requirements -- not the application's core scale -- so a text classifier correctly finds most of them genuinely ambiguous on direction. This matches docs/03's own warning that amendment direction is "unknowable" in general, just not *always* unknowable.
